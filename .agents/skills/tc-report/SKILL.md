# tc-report — Bug Report Generator & GitHub Issues Creator

> **Purpose:** Analyze test execution results from `tc-execute`, classify each
> failure as a true application bug or a test/environment issue, generate a
> comprehensive Markdown bug report, and — after human confirmation — create
> GitHub Issues with screenshots attached.

## When to Use

Invoke this skill **after** `tc-execute` has completed and produced results.
This is the final step in the workflow.

**Trigger phrases:** `/tc-report`, `generate bug report`, `create bug reports`,
`analyze failures`, `report bugs`, `create issues`.

---

## Prerequisites

- `tc-execute` has been executed — `results.json` and `test-results/` exist
- `gh` CLI is installed and authenticated (for GitHub Issues)
- The repository is a git repo with a GitHub remote

---

## Input

| Source | Description |
|--------|-------------|
| `e2e/results.json` | Raw JSON test results from Playwright |
| `e2e/test-results/` | Screenshots, traces, and videos from failed tests |
| `testcase/FR_*.md` | Original test case documents for cross-reference |
| `docs/test-execution-summary.md` | Execution summary from tc-execute |

## Processing Steps

### Step 1 — Parse Failed Tests

1. Read `e2e/results.json`
2. Filter all tests with status `failed` or `timedOut`
3. For each failed test, extract:
   - Test name and TC ID
   - Project (browser) where it failed
   - Error message and stack trace
   - Screenshot path (from `test-results/`)
   - Expected vs actual values (from assertion error)

### Step 2 — Classify Failures

For each failed test, classify into one of three categories:

#### True Bug (Application Defect)
The test correctly identifies a real defect in the SUT. Indicators:
- Assertion fails because the application behavior does not match the specification
- Error is consistent across multiple browsers
- The expected value comes directly from the test case specification
- Examples:
  - `Expected: type="email" | Actual: type="text"` → UI bug
  - `Expected: redirect to "/" | Actual: stays on "/login"` → Logic bug
  - `Expected: "Đăng Nhập" | Actual: "Đăng Ký"` → Content bug
  - `Expected: HTTP 401 | Actual: HTTP 200` → Security bug

#### Script Issue (Test Code Problem)
The test script itself has a problem. Indicators:
- Locator not found (element selector is wrong)
- Timeout waiting for element that exists with different selector
- Race condition or flaky behavior
- Error only occurs in one browser (browser compatibility issue in test code)
- Examples:
  - `locator.fill: Error: strict mode violation` → Ambiguous selector
  - `Timeout 30000ms exceeded` with correct page loaded → Wrong locator
  - `Error: page.goto: net::ERR_CONNECTION_REFUSED` → Wrong URL in test

#### Environment Issue
The test infrastructure has a problem. Indicators:
- All tests fail with connection errors
- SUT returned 500 errors
- Browser crashed
- Examples:
  - `net::ERR_CONNECTION_REFUSED` for all tests → SUT not running
  - `browserType.launch: Browser closed` → Browser installation issue

### Step 3 — Cross-Reference with Test Cases

For each True Bug:
1. Find the original test case in `testcase/FR_*.md`
2. Extract the expected behavior from the specification
3. Check if the test case has a "Known Bugs" section that documents this
4. Determine bug severity:
   - **Critical:** Security issue, data loss, complete feature broken
   - **High:** Core functionality fails, no workaround
   - **Medium:** Feature partially works, workaround exists
   - **Low:** Cosmetic issue, minor UI discrepancy

### Step 5 — ⛔ Human Gate: Review Before GitHub Issues

Present the classified bug list to the user:

```
🐛 tc-report — Bug Analysis Complete

True Bugs Found: {N}

| # | Bug ID | Severity | Feature | TC | Title |
|---|--------|----------|---------|----|---------| 
| 1 | BUG-001 | High | {Feature} | {TC} | {Title} |
| 2 | BUG-002 | High | {Feature} | {TC} | {Title} |
| ... | ... | ... | ... | ... | ... |

Script Issues: {N} (documented in bug-report.md, no GitHub Issue needed)

Which bugs should I create as GitHub Issues?
- Reply "ALL" to create issues for all true bugs
- Reply with specific Bug IDs (e.g., "BUG-001, BUG-003") to select
- Reply "NONE" to skip GitHub Issue creation
```

**CRITICAL:** Do NOT create any GitHub Issues until the user explicitly responds.
This is a mandatory human confirmation gate.

### Step 6 — Create GitHub Issues (After Approval)

For each approved bug, create a GitHub Issue:

```bash
# Create the issue
gh issue create \
  --title "[BUG-{NNN}] {Bug Title}" \
  --body-file docs/bugs/BUG-{NNN}.md \
  --label "bug,automated-test,{feature-label}" \

# Upload screenshot as a comment (if screenshot exists)
gh issue comment {issue_number} \
  --body "## Screenshot\n\n![Failure Screenshot](screenshot_url)"
```

For screenshot attachment, use one of these methods:
1. Upload screenshot to the repo and reference it
2. Attach via `gh issue comment` with image markdown
3. Include base64-encoded screenshot in issue body

**Individual bug file structure** (`docs/bugs/BUG-001.md`):

```markdown
## Bug Description
{Detailed description}

## Steps to Reproduce
1. Navigate to {URL}
2. {Action}
3. {Action}

## Expected Result
{From test case specification}

## Actual Result
{From test execution}

## Environment
- Browser: {Chromium/Firefox/WebKit}
- OS: {OS}
- SUT Version: {commit hash}

## Test Evidence
- Test Case: {TC ID} from {Feature}
- Playwright Report: {link}
- Assertion Error: `{error message}`

## Severity
{Critical/High/Medium/Low} — {Justification}
```

### Step 7 — Update Execution Summary

Update `docs/test-execution-summary.md` with:
- Bug report link
- GitHub Issue numbers
- Final classification counts

## Constraints

- **Human gate is MANDATORY** before creating GitHub Issues
- **Screenshots required** for every GitHub Issue
- **Cross-reference required** — every bug must link to its source test case
- **No false positives** — script issues must NOT be reported as application bugs
- **Vietnamese text preserved** — bug titles and descriptions may contain Vietnamese
