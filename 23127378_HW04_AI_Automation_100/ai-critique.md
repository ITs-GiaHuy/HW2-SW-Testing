# AI Critique

During this assignment, the AI demonstrated impressive capabilities in rapidly generating boilerplate automation scripts and structuring data-driven tests. However, it was far from infallible. The AI initially got several critical things wrong, particularly regarding asynchronous handling and test stability. For example, when testing the CSV import feature, the AI generated a script that triggered the file upload *before* setting up the Playwright API response listener. This race condition led to flaky tests that failed intermittently. Additionally, the AI failed to account for intentional application bugs; its generated assertions were rigidly optimistic. When a bug caused a success message to not appear, the script would simply crash with a 30-second timeout rather than elegantly catching the failure and failing the assertion immediately.

Why did the AI fail to catch these issues? Primarily because LLMs are predictive text engines trained on idealized code patterns. The AI assumed a "happy path" architecture where network requests are instantaneous and the system under test is bug-free. It lacks the contextual awareness of the local Vite server's load limitations or the specific intentional flaws injected into this assignment. It didn't "know" the backend would fail to rollback a transaction, so it wrote tests assuming standard behavior.

This experience reinforced a crucial principle about collaborating with AI: **AI is a co-pilot, not an autopilot. Human review is non-negotiable.** I learned that AI must be carefully guided with explicit constraints (e.g., "use `.catch()` to prevent timeouts on missing elements") and that its outputs must be treated as a *first draft*. The human engineer must always retain ownership of the test architecture, ensuring that edge cases, network flakiness, and specific business constraints are properly handled. Relying blindly on the AI would have resulted in an unreliable, flaky test suite that masked the true nature of the application's defects.
